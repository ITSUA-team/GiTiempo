# Design

## Context

See [proposal.md](proposal.md) for the product decision and issue #476. Current code provides most of the necessary primitives, but its boundaries enforce existing-member login:

- `apps/api/src/auth/services/auth.service.ts`: `login` requires an existing member; `createRegisteredSession` already creates a workspace, settings, admin membership, and session in one transaction. Registration additionally locks/checks normalized workspace names.
- The Firebase verified-identity interface and both implementations currently omit sign-in-provider metadata. The backend cannot safely distinguish Google from email/password login using the current interface alone.
- `apps/api/src/auth/services/auth-github.service.ts` resolves an existing member before staging a handoff. `apps/api/src/github/services/github-account.service.ts` persists OAuth credentials and a session transactionally, but requires membership to exist first.
- `apps/api/src/invites/services/invites.service.ts` may provision a Firebase identity when sending an invitation. Acceptance currently upserts the local user before its membership transaction. This path must coordinate with social provisioning, without accepting invitations during login.
- `apps/api/src/workspaces/schemas/workspaces.schema.ts` and historical migration `0010_register_lookup_uniqueness.sql` enforce `workspaces_name_lookup_unique`. UUIDs, not names, drive workspace sessions, switching, cache scope, and extension selection.
- Both web apps already bootstrap the normal token pair through shared session leaves. No new onboarding layout is necessary. The user registration composable maps the name-conflict error that is being retired.

Current auth/GitHub specs and `docs/API-ENDPOINTS.md`, `docs/DATA-MODEL.md`, `docs/PROPOSAL.md`, and `docs/github-oauth-account-linking.md` describe older restrictions. The deltas explicitly supersede them; update current docs with implementation rather than editing archived decisions.

## Goals / Non-Goals

**Goals:** Reuse the existing session and workspace foundation, make the zero-membership decision race-safe across providers and invite acceptance, and preserve identity ownership and transactional session guarantees.

**Non-Goals:** Additional-workspace creation UI (#480), new consent storage, new signup forms, changes to email/password eligibility, automatic invite acceptance, migration of existing memberships, or changes to GitHub App authorization. Existing defaults supply settings; no new billing or time-zone policy is introduced. Transferring the selected account/session between admin-web and user-web belongs to [#483](https://github.com/ITSUA-team/GiTiempo/issues/483) and is excluded from this change’s implementation and acceptance. Existing app-local session bootstrap, UUID selection and role-based redirects remain in scope.

## Decisions

### 1. One backend provisioning operation, before session issuance

Extract the small transaction-aware workspace foundation from existing registration code. Both eligible social entry points call the same operation: resolve/reuse the user, re-read all memberships, select an existing membership or create `Workspace` plus settings and `admin` membership, then issue the normal session. Keep manual registration validation and Firebase email/password creation separate.

Persist the local user, workspace, settings, membership, hashed refresh token, and (for GitHub) ownership/link and encrypted OAuth grant in the same database transaction. Generate/sign the access token before commit so signing failure rolls back; return it only after commit. Preserve avatar-source ownership rules and existing deterministic membership selection.

Alternative: frontend-created workspaces after login would require an otherwise unauthorized intermediate session and expose partial onboarding. Provisioning solely in each provider service would duplicate concurrency-sensitive behavior.

### 2. Serialize on account identity, not workspace name

Use transaction-scoped identity locks and rechecks. Reuse the normalized registration-email lock namespace where email is known, then lock the canonical Firebase UID and existing local user before evaluating memberships. Identity selection may be prepared outside the transaction but must be revalidated inside it. Every writer participating in first membership creation—Google sign-in, GitHub exchange, manual registration where applicable, and invite acceptance—must follow the same lock order. Keep GitHub generation/ownership locks after identity locks in the shared transaction path; avoid nested independent transactions.

The UID lock namespace is global across canonical and additional subjects. Every user/binding writer, including registration and invite acceptance, acquires incoming and canonical UID locks in deterministic UID order after email locks, checks the union of both stores, and only then claims a canonical UID or additional subject. Separate table uniqueness constraints cannot enforce that union alone. Invite acceptance uses the same subject/account resolver rather than upserting an alias UID as a new canonical user. Test a concurrent canonical-versus-alias claim to prove exactly one owner commits.

Move invite acceptance's local upsert into its coordinated transaction. If invite acceptance commits first, login sees that membership and creates no personal workspace. If social creation commits first, an explicitly requested invite acceptance can add the team membership; ordinary sign-in never consumes the invite. Existing unique Firebase UID, normalized user email, GitHub owner, and workspace/user membership constraints remain final guards. Re-read/retry compatible uniqueness races; reject conflicting identities without transferring ownership.

Manual registration needs a durable unknown-outcome policy because Firebase creation cannot be cancelled. Before making the Firebase request, commit a `registration` reservation under the shared email/UID locks with a random explicit UID, the normalized email, original validated display/workspace names, acknowledgement/registration intent, and lifecycle state. Never store the password. Keep the identity critical section through the normal Firebase-create and SQL-foundation path. Bound how long the request waits; a timeout, lost response, or process crash leaves the exact reservation intact and returns the stable unavailable result. It does not prove creation failed, grant a session/workspace, authorize email ownership, or permit deletion/recreation of that UID.

Later backend-verified Firebase authentication proving control of that exact reserved UID may reconcile the attempt under the same locks. Revalidate UID, normalized email, disabled state, identity ownership, and reservation state; then atomically create the original local user/workspace/settings/admin foundation using the stored names, or reuse a compatible committed foundation/membership without duplication. A different UID with the same email, an unauthenticated registration retry, or a reservation alone cannot adopt the attempt, reset credentials, mint a custom token, or change ownership. This recovery preserves manual acknowledgement semantics and never infers email consent.

Known Firebase rejection or known application failure may compensate only the unadopted UID created by that attempt, before releasing locks. If deletion/rejection is uncertain, retain the reservation and reconcile by exact UID after restart; an exact reserved UID that is temporarily absent is also not proof of final failure because late creation may still finish. Never expire, delete, or recreate that reservation solely on this observation, and never erase provenance blindly. Before a social or invite path commits a new local identity after waiting for this coordination, revalidate that the Firebase UID still exists and matches the verified account; a token verified before compensating deletion cannot authorize a dangling local user.

Alternative: checking membership before the transaction is insufficient under concurrent attempts. A global lock on `Workspace` would unnecessarily serialize unrelated users and would no longer represent a uniqueness policy.

### 3. Verify Google eligibility from trusted Firebase data

Extend `firebase-admin.interface.ts`, the real adapter, and `FakeFirebaseAdminService` to expose the provider of the verified token's actual sign-in. Only verified Google sign-in enters automatic provisioning through `/auth/login`; the presence of a linked Google provider on a password-authenticated account is insufficient. Do not add a request-body provider switch or relax identity/email collision handling. Keep existing-member login behavior for other supported providers.

The hermetic fake must express Google versus password tokens deterministically while retaining existing fixtures' default meaning. Update adapter, auth, invite, and E2E tests together. The final implementation must verify the SDK's decoded-token field in current official documentation before changing the adapter.

### 3a. Independently verified Google email proof when Firebase omits it

The user approved this extension on 2026-10-27 after a real GitHub-first account's new Google Firebase subject had no top-level email. The API rejected both attempts as `missing_email`; restoring Firebase's temporary duplicate-email setting did not change the retry. Provider profile email is diagnostic information and cannot establish verification.

Allow the strict `/auth/login` request to include an optional, bounded `googleIdToken` beside `firebaseIdToken`. Verify Firebase first with revocation checking. Use the alternate proof only when its actual sign-in provider is `google.com` and the Firebase token lacks verified email. Independently verify Google's RS256 signature using Google's fixed public-key endpoint, accepted issuer, required expiry/issued-at claims and an environment-owned `GOOGLE_OAUTH_CLIENT_IDS` audience allowlist; validate an authorized party when present. An empty allowlist disables the fallback. Never accept a client-selected audience, arbitrary key URL, profile email, access token or custom token as this proof.

Require a nonempty email and boolean `email_verified=true` from the verified Google token. Its `sub` must equal the single Google subject in the already verified Firebase token's `firebase.identities['google.com']`. Reject missing, ambiguous or mismatching subjects and a conflicting present Firebase email. Under the normal identity locks, recheck the Firebase UID is live and enabled and retains that same Google provider subject; any present live account email must agree. A missing live top-level email is acceptable only with this paired proof. Do not mutate Firebase credentials or email fields to make the test pass.

This replaces only the incoming email proof. Existing-account verified ownership, contradictory-owner rejection, canonical JWT identity and atomic subject/session persistence remain required. Failure commits no local foundation, binding or session. Do not persist or log either raw credential; redact `googleIdToken` at request-log boundaries. Use bounded key caching, fixed endpoints and request timeouts, with no new dependency.

Explicit invitation acceptance uses the same identity verifier and optional bounded `googleIdToken` before comparing the proved email to the invitation. Carry the paired Google subject into the locked live-identity recheck and persist a verified Google alias only within successful membership/invitation mutation. Do not call ordinary social login first: an invitation-first flow must not create an unsolicited personal workspace. Login evaluates exact-UID pending-registration recovery before social provisioning, including when the verified email came from paired Google proof.

Linked GitHub ownership authenticates the immutable link without asserting that its local email is provider-verified. Without actual verified incoming email evidence, no verified-email binding is created. Credentialless GitHub/invitation creation rejects manual-registration reservations without mutating them; compatible credentialless purposes may share their creation provenance. Recheck a newly adopted GitHub Firebase UID after identity-lock waits before committing its account and workspace.

Both web popup flows preserve the Google credential's ID token for the immediate backend exchange, without storing it. The extension must obtain an actual Google ID token through a documented OpenID Connect flow with `openid email` scopes, state and a fresh nonce, then pair it with its Firebase token. Its configured OAuth audience remains separate per environment; an access-token-only result cannot substitute. No new user-facing fields or onboarding screen are introduced.

The extension validates the exact callback origin/path, fragment-only credentials, one exact state and an ID-token nonce matching the attempt. Reject duplicate consumed security fields, including `iss`. If authorization-response `iss` is supplied, require exactly `https://accounts.google.com`; historical responses without it remain compatible. Ignore unconsumed metadata such as `authuser` and `prompt`. The API independently verifies the signed Google token, whose documented legacy issuer spelling remains accepted. Safe failure reasons identify the failed check without exposing callback or credential values. This follows [Google's OIDC response contract](https://developers.google.com/identity/openid-connect/reference), [RFC 9207](https://www.rfc-editor.org/rfc/rfc9207.html#section-2.4) and the [OAuth requirement to ignore unrecognized response parameters](https://developers.google.com/identity/oauth2/web/guides/use-code-model).

Verify successful missing-email binding, ordinary verified-Firebase login compatibility, invalid signature/issuer/audience/authorized-party/time claims, unverified email, subject/email mismatch, disabled/deleted live identity, absent proof and failure cleanup. Repeat the real GitHub-first → Google flow after local deployment and confirm one original account/workspace, an additional subject and usable-alternative disconnect behavior.

References: [Google ID-token verification](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token), [Firebase Google sign-in](https://firebase.google.com/docs/auth/web/google-signin), [Firebase token verification](https://firebase.google.com/docs/auth/admin/verify-id-tokens).

### Canonical account binding and recoverable identity creation

The confirmed product policy is one GiTiempo account for Google and GitHub with the same normalized verified email only when both sides prove that email. Resolve both Firebase subject and verified email under the shared locks. Incoming provider verification proves only the incoming identity; the existing account also needs durable evidence for the same normalized verified email, such as its current verified canonical Firebase identity or a proven prior verified social binding. Preserve `users.firebaseUid` as the canonical provisioning/recovery UID and continue issuing application JWTs from that persisted canonical value. An incoming Google UID may differ and may bind only after this two-sided proof. No Firebase custom token, credential mutation, or Firebase account merge is needed to issue the application's own session.

Persist additional verified Firebase subjects in a small subject-binding store: globally unique Firebase UID, local user foreign key, verified provider/email evidence, and timestamps. Check the union of canonical and additional subjects under shared UID locks; no subject can belong to two users, including canonical-versus-alias collisions. Install a binding for the incoming Google subject atomically with account/session persistence. An already bound subject continues to identify its owner when provider profile email changes; do not move a binding by email. When subject lookup identifies user A and verified email identifies user B, reject if A differs from B. Existing immutable GitHub links likewise retain precedence. A local `users.email`, pending invitation, or creation reservation alone cannot supply the existing-side verification proof; credentialless invitation provenance may establish reuse of that invitation-created UID but does not verify a password account's email. An unverified manual password-registration email must return safe identity-proof recovery without a session, subject binding, merge, or ownership transfer. Do not backfill proof from local email values, legacy invitations, reservations, unverified profile metadata, or mere provider presence. Keep profile synchronization from overwriting the canonical UID or another account's normalized email.

Google-first then GitHub reuses the canonical account through GitHub's verified-email resolution. GitHub-first then Google binds Google's verified subject to that same local account even if Firebase supplies a different UID. Concurrent compatible sign-ins converge on one local user/workspace; incompatible existing bindings fail without merging accounts. A binding conflict gives existing-account sign-in/support recovery guidance without an additional onboarding step on ordinary success. Firebase account-per-email configuration must be documented and covered by provider smoke tests, but identical Firebase UIDs are not a prerequisite for the confirmed product behavior.

GitHub disconnect currently tests alternative credentials only on `users.firebaseUid`. Extend that safety check to the canonical UID and durably proven additional Firebase subjects of the same local user, querying live Firebase provider availability and disabled state. Historical Google sign-in evidence alone is insufficient to assert an alternative credential still works. Never claim a bootstrap canonical UID acquired a Google credential merely because another subject authenticated the account. JWT/refresh and application access continue using the stable local user, canonical claim, and workspace membership.

Add a small durable identity-creation reservation store with unique normalized email and reserved Firebase UID, purpose (`github-signin`, `invitation`, or `registration`), lifecycle state (`reserved`, `confirmed`, `bound`), timestamps, and the immutable non-secret manual-registration payload needed only for `registration`. Transition to `bound` with local-user/subject binding in the same final SQL transaction; a `reserved` or `confirmed` record can survive failed onboarding. Before an eligible GitHub exchange, invitation send, or manual registration creates a Firebase identity, commit the reservation with a random explicit UID under the email lock. This separate commit grants no session, local user, workspace, membership, GitHub ownership, or email-ownership proof. Create Firebase using that exact reserved UID; after timeouts or crashes, reread by reserved UID and verify its email before marking creation confirmed. A reserved UID is never reassigned. Serialize creation/final adoption with the same identity lock order; do not hold a caller's SQL transaction while independently committing the reservation. A failed create whose outcome is unknown retains its reservation for reconciliation; do not delete/recreate it on timeout.

Background reconciliation may update only the reservation's lifecycle state from checks of the exact reserved UID and matching normalized email. It cannot create a local user, workspace, membership, or session; completing a manual-registration foundation requires backend-verified authentication proving control of that UID.

An existing Firebase identity may be used after either (a) a local account already binds that exact UID, (b) a verified Firebase token proves the current initiator controls it, or (c) a credentialless GitHub/invitation creation reservation proves GiTiempo created that exact UID and the current verified provider email matches. Option (c) never applies to a pending manual-registration reservation. Revalidate existing bindings, email, and creation state before adoption. A Firebase email lookup or a pending invitation alone is not creation provenance. Existing unbound legacy identities without proof require existing-provider authentication/credential linking and retry; never mint a custom token or mutate credentials solely from their email match. Do not backfill provenance from legacy invitations or provider metadata. New invitation sends use this reservation path; legacy invitations remain pending and usable through normal identity-authenticated acceptance.

This store is necessary because an external Firebase creation can survive a failed SQL transaction without leaving a local user. Retaining its committed reservation allows a later verified exchange or exact-UID manual-authentication recovery to retry safely without treating arbitrary Firebase users as application-created. Manual registration uses the same retained-identity lifecycle while retaining narrowly guarded compensation for known failures. Migration adds reservation fields without passwords or credential material and an additional-subject store; canonical subjects remain represented by existing user rows, and no credential or user backfill is required.

Official behavior references: [Firebase Admin user management](https://firebase.google.com/docs/auth/admin/manage-users) documents lookup and explicit UID creation; [Firebase account linking](https://firebase.google.com/docs/auth/web/account-linking) requires proof of the existing account for credential conflicts. Email lookup does not supply application creation provenance.

### 4. Extend GitHub staging without weakening handoff verification

Keep start, callback, and exchange endpoints. During callback resolve a discriminated candidate: existing account by immutable GitHub link; existing account by verified-email rules; or new account by safely selected verified email. Stage its immutable GitHub ID, safe identity/profile information, encrypted grant, and applicable authorization generation in the existing expiring handoff store. Keep account data out of redirects. No durable local account/workspace or Firebase creation occurs in callback.

Resolution order preserves existing active-member behavior only where the candidate also has existing-side verified-email proof. Without an immutable link, first evaluate such active-member matches using all verified emails and the existing primary-email tie-break. If none match, evaluate zero-membership local accounts with the same two-sided proof: reuse the sole match or the uniquely matching verified primary email; reject ambiguity. A local email match without proof returns identity-recovery guidance and is never staged as that account. With no safely resolved local match, select verified primary email, otherwise the sole verified email; reject multiple verified emails without a usable primary. A linked owner with zero memberships remains the owner and gets their own workspace; do not fall through to another email. Existing different-GitHub-ID and cross-user link conflicts remain errors.

After handoff consumption and initiator proof, reuse the bound canonical Firebase UID or resolve/create it through the reservation policy above. Reuse invitation-created identities only with the recorded creation proof or verified Firebase control. Then revalidate candidate ownership and email mapping under identity locks, recheck generation, provision only if membership is still absent, and commit through the transaction-aware OAuth/session operation. Refactor `saveOAuthAndRun`'s existing-member precondition at this boundary; do not bypass ownership checks.

An existing-account candidate carries its captured authorization generation and original flow start time. A new-account candidate explicitly carries the initial generation (`0`) and the same start time rather than omitting version checks. Once its canonical user is resolved under lock, compare the persisted generation and disconnect timestamp to that expectation before ownership or credential writes. A compatible account created concurrently can be reused only if those checks still pass; a link/disconnect between callback and exchange invalidates the older candidate.

Web cookie binding, extension verifier binding, replay consumption, expiry, configured redirect destinations, and actual granted-scope recording remain enforced. Optional feature-scope omissions do not block otherwise valid sign-in. OAuth sign-in does not create a personal GitHub App grant or workspace installation.

Firebase is outside the SQL transaction. Reuse an authorized existing identity without mutation. If a newly created GitHub Firebase identity outlives a failed database transaction, retain it and its creation reservation for a safe retry and emit a sanitized operational failure; no local workspace/session is committed. Do not apply destructive compensation to this reusable social identity, and never delete an invitation identity or an identity another attempt adopted. Manual registration retains cleanup for its own unadopted identities, with the coordination guard in Decision 2.

Alternative: creating the account during callback would allow an abandoned or unproven handoff to leave durable onboarding. Returning no-member for an eligible verified candidate would retain the issue's failure.

### 5. Remove global workspace-name uniqueness everywhere

Remove `workspaces_name_lookup_unique` from the Drizzle schema and add a new forward migration dropping that index. Do not alter `0010_register_lookup_uniqueness.sql`. Remove name lookup, name-based advisory locking, and constraint-to-error mapping from registration. Keep user-email uniqueness and all existing name shape limits.

Retire `workspace_name_unavailable` in API registration errors, shared types/schema, user-web registration mapping, tests, and generated OpenAPI. Automatic provisioning always inserts the exact display name `Workspace`. Rename needs no name-availability check. No slug, suffix, or routing change is needed: all known consumers use workspace IDs.

Alternative: adding random suffixes would violate the chosen default and retain the unnecessary display-name constraint.

### 6. Reuse client session behavior and keep consent explicit

The API returns the existing token pair, so `packages/web-shared/src/auth/session-core.ts`, the two app auth stores, GitHub callback routes, and extension token handling can use their current bootstrap paths. Change runtime leaves only where a real consumer assumption or error mapping requires it; add behavioral coverage rather than new onboarding orchestration. Remove misleading unmatched-member copy in shared GitHub errors and both login consumers as necessary.

Do not add a social naming/owner checkbox page, submit synthetic `ownerAcknowledgement`, or write email-consent flags/events. Preserve existing preferences and manual registration's explicit acknowledgement validation. The standalone registration page continues to exclude social signup actions; automatic social provisioning starts from existing login actions.

## Risks / Trade-offs

- Identity locks across provider, registration, and invite paths can deadlock if acquired in different orders → one shared order and real-database concurrency tests, including Google/GitHub and invite races.
- GitHub now supports a pre-user candidate instead of only an existing member → discriminate staged state explicitly and keep initiator/generation/ownership revalidation at commit; test tampered, replayed, expired, and conflicting candidates.
- Firebase creation cannot roll back atomically with PostgreSQL → reuse safely on retry; retain pre-existing identities and avoid destructive cleanup on social provisioning failure.
- Identical visible names can be confusing in lists → preserve distinct IDs and current selection semantics. A new disambiguation UI is not required for #476.
- New credentials must not be interpreted as marketing consent → assert no consent/acknowledgement writes or events; no new consent storage is needed.
- Old API versions may still reject duplicate names or produce no-member → migrate first, deploy the API before relying on automatic onboarding, and retain safe client fallback for deployment skew.

## Migration Plan

1. Add and verify the forward index-drop and empty identity-reservation/subject-binding-store migrations against a migrated database; retain data and UUID/membership constraints. Do not infer provenance for legacy Firebase users. Update schema snapshots/journal by the existing migration workflow and verify both same-UID and different-UID cross-provider behavior before rollout.
2. Deploy migration before application code that repeatedly creates `Workspace`. Ship API provisioning and removal of name checks together, followed by shared/frontend error updates. No existing workspace or user backfill is required; existing zero-membership accounts become eligible on their next social sign-in.
3. Verify fresh and existing accounts, duplicate-name manual registration/rename, ordinary invite preservation and explicit later acceptance, cross-provider retries/concurrency, and all existing handoff and session-security scenarios.
4. An API rollback can stop automatic provisioning while keeping the nonunique-name schema and all created workspaces. Do not recreate the unique index while duplicate labels exist; any restoration of uniqueness requires a separate reviewed data policy. Do not delete provisioned workspaces as rollback.
