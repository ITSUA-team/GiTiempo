# Tasks

Product decisions are confirmed. These are implementation tasks; no application implementation is included in this proposal.

## 1. API — reusable workspace names

- [ ] 1.1 Remove the normalized workspace-name unique index from the Drizzle schema and add a forward drop-index migration with generated metadata; verify migration on an existing database preserves workspace IDs/data and allows two `Workspace` rows.
- [ ] 1.2 Remove registration's workspace-name lookup, advisory lock, and constraint-conflict mapping while retaining email uniqueness and name shape validation; verify unit/E2E cases for duplicate names, duplicate email, invalid names, and registration rollback.
- [ ] 1.3 Verify admin rename accepts equal and normalization-equivalent names while non-admin mutation remains forbidden; land focused workspace E2E assertions and update the name/identity policy in `docs/DATA-MODEL.md`.

## 2. API — Google provisioning and membership coordination

- [ ] 2.1 Verify the Firebase decoded sign-in-provider field using current official documentation, expose it through the real/interface/fake adapters, and retain existing fake-token fixture meaning; verify deterministic Google/password adapter tests without real credentials.
- [ ] 2.2 Extract a transaction-aware workspace/session foundation from registration and add shared identity locks with a documented acquisition order; verify that workspace, settings, admin membership, refresh persistence, and token-signing failures roll back together in real-DB tests.
- [ ] 2.3 Implement canonical account resolution by UID and normalized verified email; route eligible Google zero-membership login through the foundation, preserve canonical UID/avatar ownership, and persist uniquely owned additional verified Firebase subjects without replacing the canonical UID, and reject contradictory subject/email owners without merging. Verify verified versus unverified email, new/existing accounts, multiple memberships, forged/unsupported providers, exact name, and default settings.
- [ ] 2.4 Add the durable identity-creation reservation schema, forward migration, and coordinator with unique email/UID, purpose, lifecycle state, and timestamps; commit reservations before explicit-UID Firebase creation and reconcile timeout/crash outcomes by reserved UID. Verify no email-only provenance, no UID reassignment, compatible concurrent retries, and conflict rejection without credential mutation.
- [ ] 2.5 Route invitation identity creation through the reservation coordinator and move acceptance's local upsert/membership into the shared lock protocol; verify new invitation provenance, safe legacy unbound-identity recovery, pending invite preservation, explicit later acceptance, and acceptance-first/social-first races.
- [ ] 2.6 Extend manual registration's identity critical section through Firebase creation and guarded compensation, and revalidate identity existence before new-user adoption after lock waits; verify both registration-first and social-first races cannot delete an adopted UID or create a local user for a deleted identity, and document guarded cleanup.
- [ ] 2.7 Add real-DB same-provider and cross-provider concurrency/retry coverage: Google-first/GitHub-first with one canonical UID per local account, simultaneous same verified email, different unbound Google UIDs that safely bind by verified email, and subjects already owned by another account. Assert one local account/workspace/settings/admin membership, existing workspace reuse, and unchanged membership-bound refresh rejection.
- [ ] 2.8 Add the additional Firebase-subject binding store/migration and extend live alternative-login checks for GitHub disconnect to proven canonical/additional subjects. Verify email changes cannot transfer subject ownership, canonical-versus-alias collisions fail, disabled/deleted providers cannot bypass disconnect safety, and JWT/refresh claims remain canonical. Smoke-test same-UID and different-UID Google/GitHub orders with the deployed Firebase configuration; conflicting owners receive safe recovery guidance.
- [ ] 2.9 Assert no inferred acknowledgement/email consent, preserved preferences, and no deletion of existing Firebase identities; document canonical verified-email policy, provenance/recovery, invitation separation, and non-consent in current API/product/data-model docs and run focused auth/invite suites.

## 8. Manual acceptance testing

Run after implementation on a migrated local/test environment with real Google/GitHub sign-in configured. Use dedicated test accounts and separate browser profiles for concurrency. For each item record the environment, tested commit, client/browser, steps, expected/actual result, and pass/fail in a manual-test report alongside this change. Capture screenshots or account/workspace IDs where useful; omit passwords and tokens. Mark blocked cases explicitly and keep their checkboxes open.

- [ ] 8.1 Sign in separately with a new Google account and a new GitHub account, each without memberships. Verify immediate entry into exactly one workspace named `Workspace`, default settings, and admin access, with no naming or owner-confirmation step. Repeat the entry-point check in user-web, admin-web, and the extension with fresh accounts where needed.
- [ ] 8.2 Sign out and sign in again, reload the authenticated page, and restart the client. Verify the same local account, workspace ID, and membership are reused. Repeat with an existing local account that initially has zero memberships; verify it receives one workspace without creating a second user.
- [ ] 8.3 Test Google-first then GitHub, and GitHub-first then Google, using matching verified email. Verify both providers reach the same local account and workspace IDs. Record Firebase subjects to confirm that an additional subject, when returned, is bound without replacing the canonical UID or creating another account.
- [ ] 8.4 Sign in with an account already belonging to one workspace, then with an account belonging to several. Verify no workspace is created, initial selection follows the documented order, switching still selects the correct workspace by ID, and user/admin routing respects the existing membership role.
- [ ] 8.5 Send an invitation to a test identity with no memberships, then perform ordinary social sign-in before accepting it. Verify a personal `Workspace` is created and the invitation remains pending. Explicitly accept the invitation and verify both memberships are available. Separately check a legacy unbound Firebase identity without creation proof: verify safe identity-recovery guidance and no silent adoption or invitation acceptance.
- [ ] 8.6 Create workspaces for two separate social accounts, manually register another account with the same workspace name, and rename an existing workspace to that name. Verify duplicate names are accepted, IDs remain distinct, and permissions/data remain isolated. Check workspace selection with equal names in the web apps and extension.
- [ ] 8.7 Start sign-in for the same zero-membership account in two browser profiles, including one Google and one GitHub flow, and complete them close together. Verify at most one workspace/settings/admin-membership foundation exists and successful sessions use it. Repeat with explicit invite acceptance racing sign-in; verify the result follows the documented commit order without losing either valid membership.
- [ ] 8.8 Cancel provider authorization, abandon a GitHub callback, retry an expired handoff, and attempt to reuse a consumed handoff in the test environment. Verify clear recovery, no authenticated client state or partial workspace from rejected attempts, and a fresh sign-in can subsequently succeed. Use a controlled test failure during provisioning to check safe retry and retained identity provenance.
- [ ] 8.9 Use controlled fixtures for conflicting Firebase-subject ownership, a different GitHub ID already linked to the matched account, and missing verified email. Verify each incompatible attempt fails without account merging, ownership transfer, extra workspace, or access to another user's data.
- [ ] 8.10 Compare consent/preferences before and after automatic provisioning. Verify no acknowledgement or email-consent value/event is inferred and existing preferences are preserved. Check the login and failure states against approved `.pen` screens; record any visible discrepancy and update depicted error copy when necessary.
- [ ] 8.11 After GitHub-first then Google sign-in, verify GitHub disconnect recognizes a currently usable Google identity, including an additional Firebase subject. With a separate test account lacking a usable alternative, verify disconnect is refused with recovery guidance. Confirm an old pre-disconnect handoff cannot restore the link.
- [ ] 8.12 Remove the membership backing a test session and attempt refresh/re-entry using that session. Verify refresh is rejected and creates no workspace or replacement membership; then check a new eligible social sign-in follows the normal zero-membership provisioning policy.
