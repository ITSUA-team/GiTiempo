# Рев’ю workspace-github-installation-tracking

Дата: 25 вересня 2026. Гілка: `spec/420-workspace-github-installations`.

## Статус після виправлення

**Рекомендація: APPROVE.** Усі шість знайдених проблем і три зайві залишки прибрано.

- Board-кандидати обмежені активними проєктами поточної GitHub-організації; `NOT_FOUND` для окремої board пропускається.
- Вибір mapping і перевірка installation отримують блокування в порядку membership → policy → installation.
- Policy поза дозволеним списком повертає `github_organization_not_allowed`; видалена installation повертає `github_installation_unavailable`, змінює локальний статус і очищує token cache.
- Подія `new_permissions_accepted` для активної installation підвищує версію авторизації та очищує token cache.
- Видалені невикористані frontend wrappers ручного reverify/remove, helper екстеншена й форматувальний шум у shared index. Вигляд GitHub Workspace Access не змінювався.

Повторна перевірка: API lint і typecheck, 451 API unit-тест у 40 файлах, 247 API e2e-тестів у 19 файлах на ізольованій PostgreSQL, цільові 47 admin-web тестів, `git diff --check` і OpenSpec strict validation. Є лише відоме попередження про розсинхронізований `node_modules` і lockfile.

Нижче — первинний звіт зі станом до виправлення, збережений як історія причин змін.

## Висновок

**Рекомендація: REQUEST_CHANGES — виправити наведені проблеми перед злиттям.**

Зайві залишки коду є: невикористані frontend-операції ручного керування інсталяціями, невикористаний helper екстеншена та форматування незмінених експортів. Водночас основні зміни backend, контрактів і клієнтів потрібні для installation-based tracking.

Візуальні зміни GitHub Workspace Access прибрані: компонент картки й шаблон Settings відповідають HEAD. Нових installation-рядків, статусів, кнопок або окремої картки немає. Автоматичне знаходження та підтвердження вже встановленого App залишено.

Обсяг на початок рев’ю: 76 файлів — 38 змінених і 38 нових. Для вже відстежуваних файлів diff містить 2029 доданих і 572 видалених рядки; нові файли до цієї статистики рядків не входять. Перевірено відповідність актуальному OpenSpec та останній вимозі щодо збереження попереднього UI.

Виявлено 5 проблем P2, 1 зауваження P3 до lifecycle-поведінки та 3 кандидати на прибирання. Підтверджених P0/P1 не знайдено. Продуктовий код під час рев’ю не змінювався.

## Функціональні проблеми

### 1. P2 — стороння або видалена GitHub board може заблокувати коректний старт

Джерела: [перелік board](/Users/alexeytsukanov/Documents/work/GiTiempo/apps/api/src/tasks/services/github-task-materialization.service.ts:291), [послідовна перевірка кандидатів](/Users/alexeytsukanov/Documents/work/GiTiempo/apps/api/src/time-entries/services/time-entries.service.ts:361), [обробка помилки](/Users/alexeytsukanov/Documents/work/GiTiempo/apps/api/src/github/services/github-installations.service.ts:606).

За відсутності готового issue/repository mapping і підказки board код перевіряє всі імпортовані GitHub boards workspace через installation організації поточного issue. Якщо серед них є приватна board іншої організації або видалена board, відповідь `NOT_FOUND` перетворюється на `github_resource_unavailable` і перериває весь пошук. Це відбувається навіть коли інша board дає коректний mapping.

**Мінімальне виправлення:** відбирати кандидатів за організацією та активністю проєкту; відсутню board-кандидата пропускати. Помилки permissions/provider слід зберегти окремими помилками. У metadata імпортованого проєкту вже зберігається `githubProjectOwner`.

**Доказ:** аналіз повного шляху від переліку кандидатів до обробки GraphQL `NOT_FOUND`. Сценарій із живим GitHub у цьому рев’ю не запускався.

### 2. P2 — неактивний проєкт створює хибну неоднозначність mapping

Джерело: [resolveExistingProjectForIssue](/Users/alexeytsukanov/Documents/work/GiTiempo/apps/api/src/tasks/services/github-task-materialization.service.ts:325).

Якщо issue є на двох boards, одна з яких пов’язана з активним GiTiempo-проєктом, а друга — з неактивним, обидва project IDs потрапляють у перевірку неоднозначності. Запит отримує `github_project_mapping_ambiguous`, хоча є лише один придатний активний проєкт. Перевірка `isActive` виконується вже після вибору одного проєкту.

**Мінімальне виправлення:** враховувати активність під час формування та остаточного вибору board-кандидатів. Остаточну перевірку активності під блокуванням залишити для захисту від одночасної деактивації. Пріоритет уже наявного issue/repository mapping зберегти.

**Доказ:** статичний аналіз запитів і порядку перевірок; окремого динамічного відтворення не було.

### 3. P2 — різний порядок блокувань спричиняє deadlock

Джерела: [старт таймера](/Users/alexeytsukanov/Documents/work/GiTiempo/apps/api/src/time-entries/services/time-entries.service.ts:377), [assertCurrent](/Users/alexeytsukanov/Documents/work/GiTiempo/apps/api/src/github/services/github-installations.service.ts:330), [підтвердження installation](/Users/alexeytsukanov/Documents/work/GiTiempo/apps/api/src/github/services/github-installations.service.ts:535).

Старт таймера спочатку блокує association та organization policy, потім membership. Підтвердження/reverify спочатку блокує membership, потім policy та installation. Коли той самий адміністратор одночасно запускає таймер і повторно підтверджує App, транзакції можуть чекати одна на одну.

**Наслідок:** PostgreSQL скасовує одну транзакцію з `40P01: deadlock detected`; контрольованого retry для цього конфлікту немає. Це проблема доступності запиту, а не підтверджений обхід доступу.

**Мінімальне виправлення:** встановити спільний порядок отримання блокувань для всіх цих операцій, наприклад membership → policy → installation, враховуючи блокування обох таблиць у JOIN.

**Доказ:** відтворено точну послідовність SQL-блокувань на ізольованому PostgreSQL з тимчасовими рядками. Результат: одна операція завершилась, друга отримала `40P01`. Це SQL-відтворення порядку блокувань, не повний конкурентний HTTP-тест. Транзакції відкочено, тимчасові рядки прибрано.

### 4. P2 — заборонена організація повертає неправильну причину відмови

Джерело: [activeAssociationForOwner](/Users/alexeytsukanov/Documents/work/GiTiempo/apps/api/src/github/services/github-installations.service.ts:824).

INNER JOIN association з organization policy не розрізняє відсутню installation та організацію поза дозволеним списком. В обох випадках повертається `github_installation_required` (409). Для забороненої організації контракт передбачає `github_organization_not_allowed` (403).

**Наслідок:** доступ блокується, але користувач отримує неправильну рекомендацію щодо налаштування App. Аналогічне змішування причин є у `assertCurrent`, якщо policy видалено під час зовнішніх запитів.

**Мінімальне виправлення:** перевіряти policy окремо від наявності association та повертати відповідний domain code; повторити розрізнення всередині транзакції.

**Доказ:** тимчасовий unit-сценарій відтворив поточну відповідь `github_installation_required` для owner поза policy.

### 5. P2 — видалений App помилково визначається як тимчасовий збій GitHub

Джерела: [assertLiveInstallation](/Users/alexeytsukanov/Documents/work/GiTiempo/apps/api/src/github/services/github-installations.service.ts:914), [fetchGitHub](/Users/alexeytsukanov/Documents/work/GiTiempo/apps/api/src/github/services/github-installations.service.ts:972).

Якщо installation видалено, а webhook ще не отримано, `GET /app/installations/:id` повертає 404. Загальний helper перетворює цю відповідь на `ServiceUnavailableException`, далі — на `github_provider_unavailable`.

**Наслідок:** постійна втрата installation виглядає як тимчасова недоступність провайдера. Локальний запис лишається `verified`; автоматичне налаштування пропускає вже збережені associations, тому повторне відкриття Settings не відновить зв’язок. Старт при цьому безпечно відхиляється.

**Мінімальне виправлення:** відрізняти 404 installation від тимчасових помилок і rate limits, повертати `github_installation_unavailable`, узгоджувати локальний стан та інвалідувати пов’язані credentials.

**Доказ:** тимчасовий unit-сценарій із відповіддю 404 підтвердив неправильний код `github_provider_unavailable`.

### 6. P3 — прийняття нових permissions не інвалідує кеш активної installation

Джерело: [handleWebhook](/Users/alexeytsukanov/Documents/work/GiTiempo/apps/api/src/github/services/github-installations.service.ts:379).

Подія `new_permissions_accepted` розпізнається, але якщо installation залишається активною, обробка завершується без зміни `authorizationVersion` та без `tokenProvider.invalidate`. Це розходиться з вимогою OpenSpec інвалідувати credentials після відповідних lifecycle-подій.

**Наслідок:** кешований credential/context може залишатися до звичайного оновлення токена. Практичний вплив залежить від змінених permissions; витоку credentials або підвищення привілеїв не доведено.

**Мінімальне виправлення:** окремо обробляти зміну permissions, оновлюючи версію авторизації та кеш. Для чинної перевіреної installation можна зберегти статус `verified` після live-перевірки.

**Доказ:** тимчасовий unit-сценарій із підписаною подією підтвердив відсутність DB update та invalidation для активної installation.

## Межі перевірки та наступні дії

Живий GitHub App setup та браузерний end-to-end сценарій не запускались. Відповідність попереднього UI встановлена порівнянням вихідного коду, без нової візуальної перевірки. OpenSpec CLI повідомляє, що node_modules не синхронізовані з lockfile; сама strict validation пройшла. Production-базу не використовували. Тимчасовий PostgreSQL зупинено після завершення перевірок.

Рекомендований порядок: виправити пошук board-кандидатів і порядок блокувань; розділити причини відмови; узгодити permission lifecycle; прибрати три невикористані/шумові залишки; зберегти регресійне покриття та повторити цільові перевірки.

Цей звіт фіксує поточний стан. Наведені виправлення під час рев’ю не застосовувались.
